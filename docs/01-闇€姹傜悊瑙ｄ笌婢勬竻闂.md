# A. 需求理解与关键澄清问题

> 视角：产品研发负责人。目标是把“让用户自助创建 Skill 与 Workflow”这项早期需求，推进到一个可验证核心链路的原型。
> v3 修订：按题目要求把澄清问题收敛为 **5 个**（v2 曾补充到 10 个，已合并进下面 5 个），并增加“假设隔离表”：每个假设落在哪个配置或数据里、答案变了改哪里。

## 1. 我对需求的理解

### 1.1 一句话
让法律/合规专业人员把**自己团队的做法和合规要求**（检查清单、审阅口径、输出格式）沉淀成可复用、可组合、可验证的 AI 能力，而不必依赖厂商为每个客户定制开发。

### 1.2 谁创建、谁使用

| 角色 | 典型身份 | 在本功能中的行为 | 关心什么 |
|---|---|---|---|
| **创建者（Builder）** | 法务运营 / Legal Ops、知识管理律师（KM）、资深律师或合规负责人；厂商侧的解决方案工程师（帮客户搭模板） | 编写任务说明、维护规则包、定义输入输出、用样例和评测集调试、把多个 Skill 串成 Workflow 并提交发布 | 结果是否稳定、能否体现本组织口径、改规则是否方便、能否证明“它是按我们的标准审的” |
| **审核人（Reviewer）** | 具备资质的律师 / 合规负责人 | 批准规则包（签署审核声明）、批准 Skill / Workflow 发布、处理运行中的审批节点、逐条复核 AI 发现 | 规则来源是否可靠、版本是否可追溯、AI 结论有没有原文依据 |
| **使用者（Runner）** | 初级律师、法务专员、合规专员；也可能是业务方（如市场部在送审前自检） | 选择 Workflow → 提交材料 → 查看各步结果和最终报告 → 复核、导出 | 快、看得懂、能核对 AI 说的话是否有原文依据、出了错知道怎么办 |
| **管理者（Admin）** | 法务负责人、IT/信息安全 | 决定谁能发布、哪些工具需确认、数据保留与加密、审计留痕 | 数据保密、责任边界、可追溯 |

> 依据：Harvey 的 Workflow Builder 面向 Innovation/Knowledge 团队自助构建；Anthropic 的法律插件同样要求组织先配置自己的 playbook（见 B 调研文档）。“创建者 ≠ 使用者”是行业通行的分工，产品要同时照顾两类人。

### 1.3 用户今天怎么做、痛点在哪（以营销物料审阅为例）

**现状流程**：市场部把海报/EDM/社媒文案通过邮件、IM 或工单发给法务 → 审阅人凭经验和一份 Word 版检查清单逐条看 → 在文档里批注 → 来回 2–3 轮 → 口头或邮件“通过”。部分团队已在用通用聊天式 AI，但每人各写各的提示词。

**主要痛点**：

1. **量大且赶时间**：营销物料量大、上线时间紧，法务成为瓶颈。
2. **标准不一致**：同一类问题（“No.1”“临床证明”“限时”）不同审阅人尺度不同；检查清单在个人电脑里，新人学习成本高。
3. **重复劳动**：大部分问题是反复出现的同类问题。
4. **通用 AI 不好用**：提示词不可复用、输出格式不稳定、无法引用本公司规则；结果难以核对，律师不敢直接用。
5. **缺少留痕**：事后很难说明“当时依据哪条规则、谁复核过、用了哪个版本”。

### 1.4 自助创建能力带来的价值

- **对客户**：把隐性经验显性化（规则包 + 步骤），新人也能按统一口径产出初稿；规则变化时自己改、经审核后生效。
- **对厂商**：长尾场景（不同法域、行业、公司口径）由客户自建，厂商不必逐一定制，产品可规模化；客户沉淀的 Skill/Workflow 形成粘性；模板库可成为增长杠杆。
- **对合规治理**：Skill 有版本、有测试样例和评测分数，每次运行留存所用配置快照，比“个人提示词”更可审计。

## 2. 需要业务方确认的关键问题（按优先级，共 5 个）

| # | 问题 | 影响的决策 | 暂定假设（已在原型中实现为可配置） | 是否阻塞 |
|---|---|---|---|---|
| 1 | **客户材料能否发送到第三方大模型？**有无数据驻留、零留存、私有化部署、指定模型供应商的要求？原图 / 原 PDF 能否发送？材料与运行记录要保存多久？ | 部署形态、模型适配层、发送前脱敏、是否发送原件、静态加密与保留期、DPA | 原型只用虚构/公开材料；模型可插拔（Anthropic / OpenAI 兼容 / 模拟）；发送前把 NRIC、电话、邮箱、卡号替换为占位符；含个人信息的原件不发送；可开启静态加密与保留期 | **阻塞生产上线**（接入真实客户数据前必须确认）；不阻塞原型 |
| 2 | **适用哪些法域与规则？规则内容由谁提供、谁有资格批准、多久复审、谁担责？**（客户自有政策 vs. 厂商策划的规则包 vs. 授权法律数据库） | 规则包内容层与更新机制、审核人资格、免责与责任划分 | 法域是**运行时的显式输入**；未指定时按规则包法域推定，并在结果上标注“适用法域：新加坡（假设）”。规则包须由组织的法律审核人签署声明（姓名、执业资格、复审日期）后才能用于正式运行；示例规则包整理自公开资料，未经执业律师审核 | 原型不阻塞；**阻塞把示例规则包作为“经审核内容”对外提供** |
| 3 | **AI 输出的定位与复核要求是什么？**只是律师复核前的初稿，还是会直接给业务方？哪些步骤必须人工审批、由谁审批？ | 人工审批节点、逐条复核、引用与依据设计、免责声明、审计字段 | 一律定位为“初审草稿”；每条发现须给出原文引文和规则编号，系统确定性核对；结论核验只决定“优先复核 / 常规复核”的顺序，所有发现都需人工确认；高风险物料经法务负责人审批节点 | 可基于保守假设推进 |
| 4 | **首批目标客户与组织形态？**（律所 vs. 企业法务/合规；谁创建、谁使用；是否需要 SSO 与审计导出） | 创建界面复杂度、模板库、角色与权限、账户体系 | 新加坡及区域内的**企业法务/合规团队**；四类角色；发布须经他人审批（四眼原则）；平台内账户 + 会话 | 原型不阻塞；**SSO / 审计导出阻塞企业上线** |
| 5 | **输入材料的形态、语言与使用场景？**（文本 / Word / PDF / 图片海报 / 视频；中英文比例；网页、Word 插件还是邮件；每月量级） | 文件解析与 OCR、多模态、集成方式、性能与成本 | 支持粘贴文本、PDF（文字层）、Word、图片（本地英文 OCR）；视频与竖排中文暂不支持 | 可基于假设推进；决定下一迭代投入 |

> 公司总部在新加坡，不等于客户在新加坡或只适用新加坡法。因此法域是**每次运行的输入**、规则是**可审核的数据**而不是代码——问题 2 的答案变了，只需要换规则包、改默认值，不需要改程序。

## 3. 假设隔离表：答案变了改哪里

每个假设都落在一个可替换的位置，避免“假设写死在代码里”。

| 假设 | 隔离在哪里 | 如果答案不同，需要做什么 | 影响范围 |
|---|---|---|---|
| 可以把（脱敏后的）材料发给第三方模型 | 环境变量 `LLM_PROVIDER` / 密钥 / `*_BASE_URL`；模型适配层 `server/services/llm/` | 指向私有部署或区域端点（OpenAI 兼容接口），或只用本地模型；不改业务代码 | 部署配置 |
| 个人信息只需替换 NRIC / 电话 / 邮箱 / 卡号 | `server/core/security.ts` 的模式表；功能开关 `PII_GUARD` | 增加姓名、地址等识别器（或接 Presidio 一类服务），在同一个 Pseudonymizer 接口下扩展 | 单个模块 + 测试 |
| 原件（图片 / PDF）可发给视觉模型 | 功能开关 `VISION`；含个人信息时自动不发送 | `FEATURES=-VISION` 全部关闭 | 配置 |
| 数据保留不限期、可不加密 | `RETENTION_DAYS`、`DATA_ENCRYPTION_KEY` | 设置保留天数与 32 字节密钥；启动自检会校验 | 配置 |
| 适用法域默认新加坡 | 规则包的 `jurisdiction` 字段 + 工作流输入 `jurisdiction` | 新建该法域的规则包并经审核；运行时选择法域；不一致时系统告警 | 数据（规则包） |
| 规则包需执业律师签署、复审周期 ≤ 24 个月 | 治理流程 `server/core/governance.ts`；组织策略 `requireApprovedRulePacks` | 调整审核声明字段或复审范围；组织可关闭强制要求（会在运行上提示“未经审核”） | 单个模块 / 组织策略 |
| 发布须他人批准（四眼原则） | 组织策略 `requireDistinctApprover`、角色规则 `ROLE_RULES` | 组织管理页修改策略；或新增角色 | 组织策略 |
| AI 只能用只读工具查阅本次材料与规则包 | Skill 的 `tools` 配置 + 组织策略 allow / ask / deny | 新增工具需进入工具注册表并经代码审核；组织可把工具设为“需确认” | 工具注册表 |
| 评测标签由项目作者标注 | `testdata/eval/*.json` | 由客户法律审核人复核或重标；评测集作为数据随版本管理 | 数据 |

## 4. 哪些可以先推进、哪些会阻塞

- **可以先推进**：Skill/Workflow 的数据模型、编辑器、DAG 执行引擎、版本与审批、结果核对与评测、异常处理、模型适配层、数据保护机制——这些不依赖上述答案。
- **原型阶段的风险控制**：材料全部使用虚构或公开内容；示例规则包标注“需核对”，审核声明里写明“演示账号，非真实律师”；模型调用支持模拟模式，模拟结果在界面和报告中明确标注。
- **会阻塞后续开发的**：
  - 问题 1（数据合规）→ 阻塞接入真实客户数据与生产部署；
  - 问题 2 中“厂商是否对规则内容负责、谁有资格批准” → 阻塞“官方规则包/模板市场”这类内容产品；
  - 问题 4 中 SSO 与审计导出 → 阻塞企业上线。

**对“规则包未经新加坡执业律师审核”这一限制的理解**：这首先是内容责任问题，其次才是技术问题。开发能做的是让“未经审核的规则不能进入正式结论”这件事被系统强制执行、被记录、可追溯；真正的审核必须由客户指定的、具备资质的人完成。因此原型把它实现为治理流程，而没有声称“已完成律师审核”。
